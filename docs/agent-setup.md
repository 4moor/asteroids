# Стартовые настройки агента

Репозиторий содержит минимальный рабочий набор. Сначала проверьте его
на своей задаче, затем меняйте инструкции по наблюдаемой причине.

| Назначение | Codex | Claude Code |
|---|---|---|
| Общие инструкции | AGENTS.md | CLAUDE.md импортирует AGENTS.md |
| Инструкции симуляции | src/game/AGENTS.md | src/game/CLAUDE.md импортирует соседний AGENTS.md |
| Skills | .agents/skills/ | .claude/skills/ |
| Настройки клиента | .codex/config.toml | .claude/settings.json |
| Политика команд | .codex/rules/publish.rules | permissions в settings.json |

Skills `verify-change` и `prepare-pr` ссылаются на общие документы
в `docs/workflows/`. У каждого клиента есть нативный файл SKILL.md.
Глобальные настройки, модели и авторизация остаются у пользователя.

## Проверить загрузку

Запустите выбранный агент из корня репозитория.
В Codex разрешите загрузку проектной конфигурации, когда клиент спросит
о доверии к проекту; непрочитанная конфигурация сама себя доверенной не делает.
Откройте `/skills` и найдите verify-change и prepare-pr.
В Claude Code проверьте `/memory` и вызовите `/verify-change`.
В Codex вызовите `$verify-change`.

Попросите агента назвать команду проверки симуляции и применимые
инструкции. Подтверждением служат прочитанные файлы и выполненные действия.

## Rules и permissions

В Codex режим workspace-write ограничивает запись рабочей папкой.
On-request разрешает запросить дополнительный доступ, когда он нужен.
Точные возможности зависят также от глобальных и управляемых настроек.

Правила команд можно проверить без выполнения самой команды:

```sh
codex execpolicy check --pretty --rules .codex/rules/publish.rules -- git push origin feat/example
codex execpolicy check --pretty --rules .codex/rules/publish.rules -- gh pr merge 1 --squash
codex execpolicy check --pretty --rules .codex/rules/publish.rules -- git status
```

Первые два примера должны найти правило `prompt`, последний — не найти
совпадение в данном файле. Эти правила сопоставляют префиксы команд вне
песочницы. Другие формы команд и вызовы MCP имеют собственные механизмы
контроля. Инструкция AGENTS.md не заменяет техническое ограничение доступа.

После изменения инструкций и rules начните новую сессию для проверки.
На семинаре сравнивайте действие до и после изменения, например выбор
тестов, использование инструмента или лишний запрос подтверждения.

## Сравнить проектный слой

Ветка `control` содержит готовую игру до добавления агентских файлов.
Тег `workshop-start` фиксирует исходную версию с настройками.
Сравните их в отдельных клонах и новых сессиях, используя одинаковую задачу
и модель. Перед сравнением проверьте, что исходники игры, тесты и зависимости
в этих версиях совпадают.

Личные и системные настройки продолжают действовать в обоих случаях.
Сравнение относится к проектному слою. Один запуск даёт наблюдение,
но не надёжную оценку ускорения или качества.

## Следующие упражнения

1. Измените одно правило или шаг skill и проверьте эффект на небольшой задаче.
2. Подключите [готовый MCP](mcp-and-plugins.md) и используйте его результат.
3. Добавьте свою миссию и проведите её через PR.
4. Упакуйте один workflow в локальный plugin и проверьте загрузку в другом
   учебном клоне. Используйте формат установленного клиента.
