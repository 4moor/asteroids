# Стартовые настройки агента

> Вы открыли контрольный вариант без проектных агентских файлов.
> Ниже описан настроенный снимок workshop-2026-09-28-configured
> и порядок сравнения с этим вариантом.

Репозиторий содержит минимальный рабочий набор. Сначала проверьте его
на своей задаче, затем меняйте инструкции по наблюдаемой причине.

| Назначение | Codex | Claude Code |
|---|---|---|
| Общие инструкции | AGENTS.md | CLAUDE.md импортирует AGENTS.md |
| Инструкции симуляции | src/game/AGENTS.md | src/game/CLAUDE.md импортирует соседний AGENTS.md |
| Skills | .agents/skills/ | .claude/skills/ |
| Настройки клиента | .codex/config.toml | .claude/settings.json |
| Политика команд | .codex/rules/publish.rules | permissions в settings.json |

Skills verify-change и prepare-pr ссылаются на общие документы
в docs/workflows/. У каждого клиента есть нативный файл SKILL.md.
Глобальные настройки, модели и авторизация остаются у пользователя.

## Проверить загрузку

Запустите выбранный агент из корня репозитория.
В Codex разрешите загрузку проектной конфигурации, когда клиент спросит
о доверии к проекту; непрочитанная конфигурация сама себя доверенной не делает.
Откройте /skills и найдите verify-change и prepare-pr.
В Claude Code проверьте /memory и вызовите /verify-change.
В Codex вызовите $verify-change.

Попросите агента назвать команду проверки симуляции и применимые
инструкции. Подтверждением служат прочитанные файлы и выполненные действия.

## Автоматическая проверка действий

Codex после доверия проекту использует:

```toml
sandbox_mode = "workspace-write"
approval_policy = "on-request"
approvals_reviewer = "auto_review"
```

Запрос дополнительного доступа оценивает отдельный агент-ревьюер: он может
разрешить действие или отклонить его с объяснением. Песочница сохраняется.
Режим можно явно выбрать командой `codex --approve-for-me`; текущий выбор
проверяется через /permissions. Обязательные политики окружения продолжают действовать.

Для Claude Code запускайте:

```sh
claude --permission-mode auto
```

Отдельная модель-классификатор проверяет действия, требующие такой оценки.
Поддержка зависит от модели и настроек организации. В современных версиях
Auto уже может быть режимом по умолчанию; явный флаг делает выбор понятным.

`permissions.defaultMode: "auto"` игнорируется в .claude/settings.json
и .claude/settings.local.json, поэтому проект не задаёт его в этих файлах.
Постоянный выбор можно сделать в личном ~/.claude/settings.json.

### Кто подтверждает публикацию

- Codex: decision = "prompt" направляет подходящий запрос активному ревьюеру.
  При auto_review это автоматическая проверка; обязательного ручного
  подтверждения такое правило не гарантирует.
- Claude Code: явные permissions.ask продолжают требовать решения человека
  в Auto. В проекте они заданы для git push, gh pr create и gh pr merge.
- Разрешение выполнить команду не выдаёт права GitHub и не заменяет ревью PR.
  Для студенческого PR по-прежнему нужны одобрение владельца и успешный CI.

### Сравнение с ручным режимом

Из корня проекта запустите новую сессию:

```sh
codex -c 'approvals_reviewer="user"'
```

Для Claude Code:

```sh
claude --permission-mode manual
```

Сохраняйте одинаковыми задачу, модель и исходный код. Проверьте выбранный
режим в клиенте. Поддержка флагов проверена на Codex CLI 0.157.1 и Claude Code 2.1.283.

[Codex Auto-review](https://learn.chatgpt.com/docs/sandboxing/auto-review),
[Claude Code permission modes](https://code.claude.com/docs/en/permission-modes).

## Rules и permissions

В Codex workspace-write ограничивает запись рабочей папкой.
On-request разрешает запросить дополнительный доступ; в стартовой
конфигурации его оценивает Auto-review.

Правила команд можно проверить без выполнения самой команды:

```sh
codex execpolicy check --pretty --rules .codex/rules/publish.rules -- git push origin feat/example
codex execpolicy check --pretty --rules .codex/rules/publish.rules -- gh pr merge 1 --squash
codex execpolicy check --pretty --rules .codex/rules/publish.rules -- git status
```

Первые два примера должны найти правило prompt, последний — не найти
совпадение в данном файле. Эти правила сопоставляют префиксы команд вне
песочницы. Другие формы команд и вызовы MCP имеют собственные механизмы
контроля. Инструкция AGENTS.md не заменяет техническое ограничение доступа.

После изменения инструкций и rules начните новую сессию для проверки.
Сравнивайте действие до и после изменения: выбор тестов, использование
инструмента или лишний запрос подтверждения.

## Сравнить проектный слой

Актуальная пара снимков на 28 сентября 2026 года:

- `workshop-2026-09-28-configured` — версия с настройками;
- `workshop-2026-09-28-control` — тот же код игры без агентских файлов.

Ветка control обновляется из main обычным слиянием, затем из её дерева
удаляется агентский слой. Исходники игры, тесты, зависимости, CI и игровые
документы в паре должны совпадать. Отличия допускаются в агентских файлах
и пояснениях к сравнению в README и этом документе.

Сравнивайте снимки в отдельных клонах и новых сессиях с одинаковыми
задачей и моделью. Для контрольного запуска не передавайте флаги,
включающие настройки из сравниваемого проектного слоя.

Личные и системные настройки продолжают действовать в обоих случаях.
Один запуск даёт наблюдение, но не надёжную оценку ускорения или качества.

Старый тег workshop-start сохраняет историческую версию с настройками,
созданную до изменения целей миссий. Он не образует пару с текущей main.
Теги с датой не передвигаются: для следующего сравнения создаётся новая пара.

## Следующие упражнения

1. Измените одно правило или шаг skill и проверьте эффект на небольшой задаче.
2. Подключите [готовый MCP](mcp-and-plugins.md) и используйте его результат.
3. Добавьте свою миссию и проведите её через PR.
4. Упакуйте workflow в локальный plugin и проверьте загрузку в другом клоне.
